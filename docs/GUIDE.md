# 책다듬이 문서 안내서 (처음 읽는 사람용)

> 이 문서는 사람을 위한 설명서다. 정확한 값(API 필드, 시간 제한 등)은 여기 쓰지 않고 링크만 건다.

## 0. 3분 요약

- **`docs/`는 지금 코드가 어떻게 동작하는지 적은 곳**이다. 노션·PDF는 과거 기록이다.
- 기능을 찾을 때는 `docs/domains/<도메인>/`을 본다. 도메인은 reading · review · reward · dday · user 다섯 개다.
- **API·DB·규칙이 바뀌는 작업은 스펙부터 쓴다.** 요청서(requirements) → 설계서(design) → 작업 목록(tasks) 순서다.
- 사람은 요청서와 설계서를 **두 번 확인**하고, AI는 작업 목록을 하나씩 구현한다.
- **문서 먼저, 구현 나중.** 구현하다 설계가 안 맞으면 AI는 멈추고 묻는다. 사람이 방향을 주면 문서부터 고치고 이어간다.
- 스펙이 끝나면 마지막에 `docs/domains/`를 지금 코드에 맞게 고친다.

## 1. 왜 이렇게 관리하나요?

중간고사 무렵까지 설계는 노션과 PDF로 정리했다. 그런데 개발하면서 많은 부분이 바뀌었다.

- DB는 MySQL로 적혀 있었지만 실제로는 PostgreSQL(Supabase)을 쓴다.
- 평점과 한줄평은 테이블 두 개로 설계했지만 실제로는 리뷰 하나로 합쳤다.
- 보상은 "완독하면 지급"으로 설계했지만 실제로는 독서 완료 화면에서 세션마다 지급한다.

설계서와 코드가 다르면 사람도 헷갈리고, AI는 더 쉽게 틀린다. 옛 설계서를 근거로 멀쩡한 코드를 "고치는" 일이 생긴다.
그래서 두 가지를 정했다.

1. **기준을 하나로.** 지금 코드를 설명하는 문서는 `docs/` 한 곳에만 둔다.
2. **순서를 고정.** 앞으로는 문서(스펙)를 먼저 쓰고 확인한 뒤 구현한다. 그래야 문서가 코드보다 뒤처지지 않는다.

이렇게 AI가 일할 환경(문서·규칙·검사 도구)을 갖추는 일을 **하네스 엔지니어링**이라고 부른다.

## 3. Part B. specs (작업 계획) 쓰는 법

### 집 짓기에 비유하면

| 단계 | 비유 | 답하는 질문 |
|---|---|---|
| requirements | 건축주 요청서 | **무엇을** 원하나? 언제 "됐다"고 볼까? |
| design | 설계 도면 | **어떻게** 만들까? 무엇이 바뀌나? |
| tasks | 공정표 | **어떤 순서로**, 한 번에 얼마씩? |

### 흐름

```
① 한 줄 요청            "세션 저장할 때 문장도 저장되게 해줘"
② AI가 requirements 작성 → ✋ 사람 확인 ("R1.3은 빼자")
③ AI가 design 작성      → ✋ 사람 확인 → approved
④ AI가 tasks 작성하고 하나씩 구현·검증
⑤ 마지막 작업: docs/domains 반영 → done
```

사람이 할 일은 ①과 두 번의 ✋다. 코드를 한 줄씩 보는 대신 "요구사항이 맞나?", "설계가 맞나?"만 확인한다.

### 언제 스펙을 써야 하나

- **써야 한다:** API(주소·필드), DB(테이블·컬럼), 비즈니스 규칙(경험치·시간 제한 등)이 바뀌거나, 두 파트 이상에 걸친 작업
- **안 써도 된다:** 단순 버그 수정, 화면 모양, 문구. 단 docs에 적힌 내용이 바뀌면 문서는 같이 고친다.

### 구현하다 설계가 안 맞으면

AI는 혼자 판단해서 바꾸지 않는다.

```
멈춤 → "설계는 A인데 실제로는 B라서 안 됩니다. 선택지: 1) … 2) …" 보고
     → 사람이 방향 결정
     → design의 '변경 기록'과 tasks를 먼저 고침
     → 구현 재개
```

규칙 전체(S1~S11)는 [specs/README.md](./specs/README.md)에 있다.

## 4. 둘이 어떻게 이어지나

```
docs/domains (현재 모습) ──읽고 시작──▶ 스펙 (바뀔 모습) ──구현──▶ 코드
        ▲                                                         │
        └─────────────── 마지막 작업: 현재 모습으로 반영 ◀──────────┘
```

- 스펙은 **바뀔 모습**, `docs/domains/`는 **현재 모습**이다.
- 구현 전에 `domains/`를 먼저 고치지 않는다. 아직 없는 기능이 있는 것처럼 보이기 때문이다.
- 스펙이 끝나면 `domains/`가 갱신되고, 다음 스펙은 그 문서를 읽고 시작한다. 이 고리가 끊기지 않게 하는 것이 핵심이다.

## 7. 자주 묻는 질문

**Q. 문서와 코드가 다르면 어떻게 하나요?**
코드가 맞다. 다른 점을 찾으면 그 문서의 담당 역할에게 알리고, 단순 누락이면 바로 문서를 고친다. 의도된 변경이 필요하면 스펙을 만든다.

**Q. 노션에 있는 설계는 안 보나요?**
참고만 한다. 무엇이 어디로 옮겨졌는지는 [archive/README.md](./archive/README.md)에 있다.

**Q. 작은 버그 하나 고치는데도 스펙을 써야 하나요?**
아니다. API·DB·규칙이 안 바뀌면 바로 고친다.

**Q. 스펙 규칙 자체를 바꾸고 싶으면?**
[specs/README.md](./specs/README.md)를 고치고 [decisions/](./decisions/)에 이유를 남긴다. 새 스펙부터 적용된다.

**Q. AI에게 일을 시킬 때 뭐라고 하면 되나요?**
"스펙 NNN의 다음 작업 진행해", "새 스펙: ○○○"처럼 말한다. AI는 루트 `AGENTS.md`를 따라 필요한 문서를 읽는다.

**Q. 비밀번호나 API 키는 어디에 적나요?**
문서에는 적지 않는다. 환경변수 이름만 적는다.
