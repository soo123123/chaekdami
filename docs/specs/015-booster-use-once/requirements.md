# 015 · 부스터 사용 중복 방지 — Requirements

## 1. 배경

- 대상: [ISSUE-BUG-33](../../known-issues.md#issue-bug-33). 부스터 사용(`POST /api/rewards/boosters/use`)은 요청이 올 때마다 1개를 쓴다 (`BoosterService.use`). 서버는 처리했는데 응답만 끊기면 앱에는 실패로 보여, 다시 누르면 하나 더 쓰일 수 있다. 코드로 확인했고 재현하지 않았다.
- 앱(`HomeScreen.handleUseBooster`)은 실패하면 "부스터를 사용하지 못했어요."를 보여주고 보유 개수를 다시 조회한다. 조회도 실패하면 버튼을 막는다. 남는 문제는 두 가지다.
  - 이미 쓰였는데 사용하지 못했다고 안내해, 다시 누르기 쉽다.
  - 앱은 10초를 기다리고 포기한다 (`apiClient.ts`). 서버가 그 뒤에 처리하면, 다시 조회한 개수는 아직 줄지 않은 개수일 수 있다.
- 부스터 개수는 상점 구매와 부스터 사용에서만 바뀐다 (`ShopService.purchase`, `BoosterService.use`).
- 사람 결정 (2026-11-25, BE2): 앱이 알고 있는 보유 개수를 함께 보내고, 서버의 개수와 다르면 쓰지 않는다. 요청 번호를 저장하는 방법(DB 테이블 추가)과 앱만 고치는 방법은 고르지 않았다.
- 구현은 스펙 009(부스터 읽는 시간 기준, `feature/009-booster-reading-time`)가 병합된 뒤에 한다. 같은 `BoosterService`를 고친다.

## 2. 요구사항

### R1. 같은 사용이 두 번 처리되지 않는다 (서버)

사용자로서, 응답이 끊겨 다시 눌러도 부스터가 하나만 쓰이기를 원한다.

- **R1.1** 요청에 보낸 보유 개수가 서버의 개수와 같으면, 부스터 1개를 쓰고 지금과 같은 응답을 준다.
- **R1.2** 요청에 보낸 보유 개수가 서버의 개수와 다르면, 부스터를 쓰지 않고 409로 답한다.
- **R1.3** 같은 보유 개수를 보낸 요청 두 개가 동시에 오면, 하나만 처리하고 다른 하나는 409로 답한다.
- **R1.4** 서버의 개수가 0이어도 보낸 보유 개수가 1 이상이면, "부스터 없음"(`REWARD_006`)이 아니라 R1.2처럼 409로 답한다.
- **R1.5** 보낸 보유 개수와 서버의 개수가 모두 0이면, 지금처럼 400 `REWARD_006`으로 답한다.
- **R1.6** 보유 개수를 보내지 않으면, 지금처럼 처리한다 (앱을 고치기 전 버전).
- **R1.7** 보낸 보유 개수가 음수이면, 400 `VALIDATION_ERROR`로 답하고 부스터를 쓰지 않는다.
- **R1.8** R1.2의 409는 요청이 겹쳤을 때의 409(`CONCURRENCY_001`)와 구분할 수 있는 코드로 답한다.

### R2. 앱이 실제 결과를 알린다 (FE2)

사용자로서, 부스터가 이미 쓰였는지 알고 다시 누를지 정하고 싶다.

- **R2.1** 부스터를 쓸 때, 앱이 화면에 보여준 보유 개수를 함께 보낸다.
- **R2.2** 보유 개수가 달라 409를 받으면, 보유 개수를 다시 조회하고 다시 사용하는 요청을 자동으로 보내지 않는다.
- **R2.3** 사용에 실패한 뒤 다시 조회한 개수가 보낸 개수보다 1개 적으면, "사용하지 못했어요" 대신 이미 사용됐다고 안내하고 부스터 위젯도 갱신한다.
- **R2.4** 다시 조회한 개수로 사용 여부를 알 수 없으면(조회 실패 등), 개수를 다시 확인하기 전까지 버튼을 막는다.
